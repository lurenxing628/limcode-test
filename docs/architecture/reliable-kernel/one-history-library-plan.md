# 每个数据目录只保留一个历史库

本文是分期方案，不是机器合同；各期落地时以 AGENTS.md、`01-invariants-and-authority.md` 和合同 JSON 的改写为准。方案与七项决策由维护者于 2026-10-07 确认。

## 目标

一个数据目录（配置根）只有一个当前历史库。旧版本按工作区分库留下的库、用户保留的库、“归档并重置”的归档、数据目录迁移挪开的拷来目录，最终都并进当前库；之后删除“切换当前历史库”、用户保留标记、多库管理、外来历史库列表与大库会话界面这一整套多库机制。

原则不变：旧历史尽量可用可读；只存在于某个旧库里的对话不能被自动删除；用户删掉的对话不能被合并插回；删除对话“该停就停，不拒绝”。

## 现状要点

- 多库相关源码约 3.4 万行、测试约 3.6 万行；9 月 20 日以来约 145 个提交在改这一块，AGENTS.md 一半以上篇幅在讲合并、外来库、迁移和清理。收敛后预计可删约 9–10k 行源码、8–12k 行测试。
- 合并引擎核心（行规则、正文传输、删除闭包、提交标记、收尾）不能删：数据目录迁移的整库分批复制与迁入已有目录都依赖它。
- 外来历史库只接受当前 epoch。epoch 升到 6 之后，所有已发布版本（epoch 3/4/5）留下的归档和拷来目录都会被判为未通过，既不能查看也不能合并，比 v0.0.36 倒退。
- 数据目录迁移的离线收尾（`relocatedWorkSettlement.ts`）已经用现有的用户停止与放弃转换收尾等待回答、子 Agent、待投递消息与进程结束通知，合并可以复用，不需要发明新终态。

## 已确认的决策

1. 以前选过“保持分开”、或标为用户保留的库，直接合并，只发一次通知。原库作为备份保留，合并进来的对话事后可以删。
2. 收不了尾的未完成工作，经用户一次确认后复用迁移的离线收尾，按“中止”处理；仍收不了的（needs_human、死宿主留下的不受支持效果、仍在运行的进程）只剔除所在对话。
3. 同 id 不同内容的冲突、坏行、缺正文，按对话剔除，其余照常合并；不给冲突对话换新 id。
4. 收不进来的部分原位保留、永不自动删除；“历史与存储管理”里只有一个“未能合并的旧数据”列表，能读的只读查看，读不出的只列位置、大小和原因。
5. “归档并重置”保留为修复入口，但改成纯备份：坏库挪到一边、新开空库，挪走的库进入残留列表，不再成为第二个历史库。
6. 当前库不搬位置：选择文件作为固定指针保留，只去掉切换。
7. 数据目录迁入已有 LimCode 数据的目录时继续合并；合并引擎、删除记录与合并账本长期保留。

## 分期

### 第 0 期：已发布格式的外来库在私有副本上升级（随 epoch 6 一起发布）

- 外来库核验接受指针、epoch 清单与库内绑定一致的已发布 epoch 3/4/5；结构仍按该 epoch 的已发布指纹精确核对，未知漂移照旧拒绝。
- 每次复制私有副本（核验审计、只读查看、合并、内容指纹、清理备份的覆盖读取）之后，在副本上执行与本地就地升级同一套 3/4/5→6 数据库升级：同一事务补表、补索引、回填时间线与已接收答案展示、插入 pending 句柄标记、重写 manifest。副本的绑定只改 epoch，身份、代数与路径保持记录值；原目录一个字节都不改，不写 journal、不做 Backup API 备份，失败或崩溃只需丢弃副本。
- 升级读正文一律经外来库现有的不跟随链接的描述符读取；epoch 3 与缺 RuntimeDeliveryIntentLink 的 epoch 4 前驱转换旧 Child continuation 时新写的正文只进私有副本旁的覆盖目录，之后的查看与合并先读覆盖目录、再读原位置。
- 审计缓存与内容指纹按“升级合同修订”区分，避免沿用旧版本对未升级副本得出的结论。
- 验收：已发布 3/4/5 的归档与拷来目录核验通过、只读查看与合并成功，合并结果与“先本地升级再合并”一致；原目录文件状态逐一不变。

### 第 1 期：不再产生新的历史库

- 去掉“切换当前历史库”；选择文件只读，作为固定指针。
- “归档并重置”改成纯备份：挪走的库只进残留列表。
- 数据目录迁移不再把其它库记为用户保留，改记为待合并；旧目录里留下的本地库纳入后续收敛。
- 删除某个旧库之前先合并（或明确确认它已被覆盖）。

### 第 2 期：一次性收敛

- 所有旧库（工作区分库、用户保留、以前切换过、外来归档与拷来目录、迁移旧目录里留下的库）统一转为待合并，启动时只通知一次，不再询问“全部合并 / 保持分开”。
- 收尾复用迁移的离线收尾，用户确认一次，原因写“合并前收尾”。
- 合并引擎增加“按对话剔除”：冲突、坏行、缺正文、收不了尾的对话子树作为跳过闭包剔除，账本记“部分合并”，剔除清单写入残留记录。
- 残留登记在当前配置根 `.limcode-runtime-merges/residual/<id>.json`：来源、位置、大小、原因、剔除的对话。
- 超过 2000 万行的库：收敛时以最大的库为目标。
- 新增“立即合并全部”的明确命令；推迟（忙窗口、空间不足等暂时性原因）维持现有行为，并常驻显示“还有 N 份没合并”。

### 第 3 期：删除多库机制

- 删除：选库与切换、用户保留标记、“以前切换过”提示、合并请求与 7 天过期、大库会话的估计与倒计时界面（保留引擎）、外来库列表与只读查看入口（改为残留查看）、“历史与存储管理”的多库部分。
- 改写：数据目录迁移（不再携带“其它数据集”、不再挪开拷来目录）、备份清理（去掉外来库分组与其它本地库的覆盖证明，新增“已合并来源”一类）、独占维护（去掉 historical-merge 操作）。
- 合同、检查器（`contract-model.mjs` 中逐字比对的代码片段）、测试清单与 AGENTS.md 同一提交改写。

### 可选

- 冲突对话按“来源身份 + 旧 id”确定性派生新 id，作为只读副本导入。
- 旧拷贝里当前库没有、又没有删除记录的对话，提供逐条找回（默认不插回）。
- 超过 2000 万行的库分批、可续地合并。

## 验证口径

每期只跑受影响的定向测试，并在真实数据副本上试跑；完整 `--ci` 回归交给 GitHub CI。
