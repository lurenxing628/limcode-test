# 协作时间线的历史合并顺序

`predecessor_message_id`、`predecessor_message_seq` 和 `position_basis` 是消息边界及其证据，不随合库重写。`exchange_seq` 是当前目标数据库中、当前 Conversation 的展示顺序；它不是跨数据库共享的时钟。

同一 Conversation 的两个独立副本可以在没有新 Message 或 Context 根的情况下各自发送协作消息，因此可能生成相同的本地 `exchange_seq`。不能把这种情况认作来源损坏，也不能分别合并接收表和发送表而改变它们在来源中的交错顺序。

普通合并与大库合并共用以下规则：

1. 先提交或准备所有引用的领域记录，再将两个时间线关系表按 `(conversation_id, exchange_seq)` 合成一个有界、逐行读取的来源流
2. 已存在的同 id 关系保留目标 `exchange_seq`，严格比较其余每一列。重复合并不移动已经展示的事件
3. 新关系按照上述来源流的顺序，由目标 writer 在同一个合并事务中共同分配接收/发送序号，接在目标当时的最大值后面。普通接收/发送不能使用这个历史导入入口
4. 新关系同时生成 `TimelineImportProvenance`，保存经过核验的来源 data-set/root-instance 身份和来源序号。它不改变消息边界证据。来源已经存在的证明在时间线关系之后原样复制，链式、往返导入保留所有证明
5. 相同证明可能已经由本事务的新关系导入步骤生成；仅在每一列完全相同的情况下复用。证明没有字段差异白名单
6. 复制到空根的迁移不是合并，保留关系及来源证明的全部原始列和序号，不重新分配

展示策略保留目标已有顺序，并保留本次新导入事件之间在来源里的顺序。独立副本在同一消息边界上发生的事件没有共同原始时钟，不能把目标先有、本次后合入的展示顺序描述为恢复出的跨副本真实发生顺序。来源中已经存在于目标的事件继续使用目标顺序，不为插入新历史而移动它们。

实现入口：`timelineMergeSource.ts` 提供共同来源流；`runtimeDataSetMerge.ts` 的规划及复用规则、`runtimeDataSetStreamedMerge.ts` 的扫描及写入都使用这个流。每批最多保留有界行数，即使整段来源被删除闭包排除也定期让出线程并检查取消；不会对每个事件重放整份历史。
