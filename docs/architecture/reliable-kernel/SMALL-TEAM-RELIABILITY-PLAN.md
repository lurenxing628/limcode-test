# 小团队项目的可靠性修复方案

日期：2026-09-22。由“核实 SQLite 锁超时根因”和“核实多项目历史切换根因”两个任务共同核对。

这是后续实施方案，不表示下列功能均已实现。当前生产边界继续以现有机器合同为准；实施涉及合同变化时只更新受影响的条目。

## 取舍

Limcode Test 是小团队项目。优先用已有机制修根因，减少需要长期维护的状态、分支和重复校验。保留防止丢历史、串工作目录和并发覆盖的检查；不引入通用迁移框架、后台协调服务、第二套锁协议或新的监控平台。

长期方向：一个配置数据根对应一个固定的当前 Runtime 数据集。项目、对话和工作环境仍独立，通过现有 Link 关联。窗口打开哪些文件夹只影响项目视图和本窗口可用目录，不决定历史存在哪个数据库。

## 先整合 PR #35

复用 PR 已有的配置增量写入、稳定更新时间、会话思维设置及 Windows Runtime claim 有界重试。它们解决不同边界的问题，不能笼统称为一次 SQLite 锁修复。

本次 Review 已修正四项行为：保存确认超时不能当成成功；历史分页按实际新布局恢复位置；子思维继承保留合法的 0/-1 预算；不兼容的父思维参数不能阻断子模型初始化。其余修复与主工作区正在开发的压缩功能分别保留，不把本地未提交改动顺带发布。

## 下一批：配置锁与实际执行目录

### 配置锁

- 沿用 `recordStore.ts` 的进程内队列和现有目录锁。JSON 配置锁与 SQLite/Runtime claim 分别处理。
- 释放时的短暂文件系统错误做有界重试，保留原始错误原因。锁已移出正式路径后的临时目录清理失败，不应把已完成的操作说成未完成。
- 对本进程确知操作已经结束但释放失败的 owner，允许下次操作前重试清理同一代锁；不得只因 PID 相同或等待超时就删除活锁。使用现有 owner token，不添加持久恢复队列。
- 区分“另一个 owner 仍持锁”和“文件系统拒绝创建/读取/重命名锁”，避免所有情况都显示争锁超时。
- 保留 PR 的内容相等则不写，不增加全局缓存或后台扫描。读配置也获取锁的现状先不扩大重构。

### 工作环境

使用已有 `ConversationProjectLink` 和传入 authority compiler 的项目 URI 计算初始执行环境，不在创建对话后追加一次配置 JSON 写入，避免 SQLite 与 JSON 各成功一半。

选择规则在前后端共用一个纯函数，优先级明确为：

1. 用户显式选择的会话环境，或子任务明确继承的父环境。
2. 对话绑定项目对应的环境。
3. 没有项目时，用户保存且仍有效的策略默认环境。
4. 没有明确默认且只有一个可用环境时，使用该环境。

策略允许范围始终生效。显式环境或项目不可用时提示重新选择，不偷偷退到另一个项目；多个候选且没有默认时也不按目录顺序或 ID 排序猜。用户主动切换才写现有 `ConversationWorkEnvironmentLink`。策略保存的默认值不得被投影改成首目录，UI 应显示真正采用的目录。

在 ProductRuntime 订阅一次文件夹变化事件，读取完整新列表，通过已有 `synchronizeWorkspaceFolders` 更新本 Host 快照并刷新 UI。沿用简单 Promise 串行化，新 Turn 等同步后再冻结；当前 Turn 保持原冻结边界。移除目录后，工具应保留其冻结根或明确失败，封住 `workEnvironmentBoundary` 到 `commandRunner` 的换根 fallback。其他窗口的目录不能被持久化成 unavailable。

## 再做：固定历史数据集，旧历史有入口

不再为文件夹组合维护长期 alias/继承图，直接复用现有同库多 Host 和对话 owner。

- 没有历史库时才新建；只有一个可用库时直接原地复用；有多个库时明确选择一套作为当前数据集，不由第一个启动的窗口抢占决定。
- 保存一个数据根级选择指针，引用完整原 Runtime root，保留原 RootBinding、dataSetId 和 CAS，不搬单个 SQLite，也不批量改对象 ID。
- 切换复用已有维护互斥与停机流程，先让使用该配置根的旧 Host 退出；普通启动只打开选定库。
- 固定选库和“其他历史库”入口同批交付。未选库完整保留，按需列举、只读分页查看；不做跨库写入或自动合并。无法确定当前项目时提供清楚的“全部历史”，不能悄悄当成“未归属对话”。
- 本批不承担跨库继续执行或汇总导入；真正需要时再做用户主动的一次离线操作。入口未实现前，不能切成默认空库并宣称历史问题已解决。
- 旧 schema 仅复用机器合同已有的有界离线升级。未知格式保留原文件并给出明确错误，不增加自动修复或通用迁移链。

## 空间管理：先让占用可解释

CAS 存有历史正文、附件和工具结果，不能整体当缓存删除。当前 `ContentObject` 合同是 insert-only / dataset-reset-only；单对象自动回收不是本轮顺带加的功能。

先在现有诊断入口提供按需分类统计：当前 CAS、SQLite、process spool、诊断文件及历史备份。按 storage key 统计物理文件，区分实际历史、临时残留和完整备份；不在启动时递归扫描。

复用已有 spool 清理、诊断轮转及数据集归档/重置。旧 scope 的整理按完整数据集呈现，用户明确选择后再处理；保留归档不会自动腾出磁盘，应清楚显示归档占用。当前数据集的历史保留量由实际使用需要决定。

固定历史库不会自动减少 CAS 文件。只有后续统计证明单对象回收收益足够大，才单独制定离线回收方案并修改当前删除约定；本轮不做在线 GC、引用计数、pack 存储或常驻扫描器。

## 最低验证与协作方式

| 改动 | 必须证明的实际行为 |
| --- | --- |
| 配置锁/保存 | 正常保存；瞬态释放失败可恢复；其他活 owner 不被误删；未确认保存不冒充成功 |
| 项目与目录 | A+B 工作区中选择 B，首个相对路径工具落到 B；显式环境和子继承优先；B 不可用不落到 A |
| 动态同步 | 添加、删除、重排目录后后台与 UI 一致，已开始的 Turn 不改根；两个 Host 的可用目录互不污染 |
| 历史数据集 | 增减目录或保存 workspace 后历史身份不变；旧库入口能看到原消息；不同对话可并行，同一对话不重复执行 |
| 空间管理 | 分类数量/大小对应实际文件；整理只作用用户选定的完整数据集；源库与 CAS 不被误删 |

复用现有测试补触发场景，一批改动集中构建、类型检查和相关回归一次。利用已通过的 PR CI，不为相同源码重复全仓套件；新增失败再扩大到受影响范围。保留外部输入、持久化提交、执行路径与并发 owner 边界的校验；不新增每次启动全库 integrity_check、CAS 哈希全扫或每层相同字段重复验证。

分工：存储任务负责配置锁、空间边界与最终 Git 集成；项目任务负责目录选择、动态同步和历史入口。共享文件串行编辑，测试完成后统一提交。当前未提交的压缩改动保留原工作区身份，不混进 PR 合并提交。
