# Agent 协作

## 用户入口与配置

全局设置一级页签「Agent 协作」集中展示派发深度、团队并发和每轮自动续派预算。Agent、对话和工作流设置提供同一组件的局部覆盖，并明确显示继承来源。数据仍写入对应作用域的 `ToolPolicy.toolConfigs.run_agent.config`，不新增第二份设置 authority。

- `maxChildAgentDepth` 默认 **1**。主对话为 0；默认可以创建子 Agent，但子 Agent 不能再新建下一层。只有用户调整设置才能增加深度。
- `maxConcurrentAgents` 默认 8，限制团队中实际活动的子 Turn，包括已预留但尚未开始采样的启动，不包含根对话或空闲成员。它与一次父 Turn 的并发启动 admission 槽位不同。
- `maxAutomaticFollowups` 默认 32，用于限制 Agent 自动续派，跨对话回复自动开启的请求方轮次也计入；0 禁止自动续派。用户明确发起的新任务与自动协作的预算来源分开。

配置在 Turn authority 中冻结，模型工具参数不包含以上设置。已有成员通信、读取和等待不增加深度。用户定制的工具允许列表继续生效，不为新增功能绕过已禁用的工具。

协作由模型工具发起，输入区不提供手动授权或留言板入口。发送消息和续派任务是两个明确动作；队列与消息状态区分已提交、已注入输入和模型已处理。

对话时间线在消息所属轮次（接收方为投递轮次，发送方为发送轮次）的首条消息处显示「来自对话 X / 发往对话 X」来源卡片，附 320 字符以内的正文摘要；对方对话已删除时显示「已删除的对话」，仍在排队等待的消息显示在时间线末尾。输入区等待队列的协作项同样显示来源对话标题。

## 身份与授权

同根团队从 `ChildExecutionParentLink` 和 Conversation/Turn 关系派生。父子树记录任务来源和生命周期；通信不改变父子树，也不把 Agent 配置作为运行地址。现有 `run_agent.send/interrupt_subtree` 仍只控制直接孩子。

团队工具不能读取、发送或唤醒团队之外的对话，也没有逐对话授权表；例外是跟进任务完成后把结果回送给原请求方，以及用户开启「跨对话协作」后的跨对话工具。跨对话工具也不能寻址任何子 Agent 对话。

模型侧使用冻结的短引用目录，内部 Conversation、消息、频道和帖子身份不直接暴露。普通请求、native 同一逻辑请求内的后续调用、压缩和重启共用持久映射；继承历史引用不授予原团队操作权限。

## 子 Agent 的工具、技能与工作环境边界（已定）

子 Agent 的每一轮只能使用它自己的设置和派出它的父对话轮次都允许的东西，和 Codex 一致：Codex 的子 Agent 从父任务的有效配置出发，角色只能收紧、不能放宽，技能也只能关不能开；Codex 当前的多 Agent 实现（V2）干脆不接受用户直接向子 Agent 输入。本项目保留在子 Agent 对话里直接输入，但这些轮次同样受下面的边界约束。

- **边界来源**：新建子 Agent 时读取父轮次冻结的工具设置（连同父轮次自己的上级边界）和技能设置，冻结进子 Agent 首轮 authority 的 `toolPolicy.inherited` 与 `skillPolicy.inherited`。之后父 Agent 或团队成员续派、用户在子 Agent 对话里输入、重试或编辑重跑，都沿用首轮这份边界。事后修改父 Agent 的设置只影响之后新建的子 Agent。
- **内置工具**：两边列表都有才提供。`submit_agent_answer` 是回答父任务的通道，只要子 Agent 自己的列表有就保留。
- **MCP**：来源两边都启用才可用；`enabledTools` 取交集，`disabledTools` 相加；父轮次没有启用的来源，在子 Agent 里关闭。
- **能否执行的设置**直接合并进子 Agent 冻结的设置：项目外路径（`allowOutsideProjectPaths`）和 ask_user、submit_plan 的自动批准须两边都开；命令黑名单相加；`maxChildAgentDepth` 取较小值。
- **按调用判断的设置**：执行确认、自动应用更改、自动提交结果和命令白名单，要子 Agent 自己和每一级上级都同意才自动或放行，自动应用的等待时间取最长。YOLO 只放宽它所在的那一级。
- **子 Agent 自己决定的**：工具参数（例如输出上限）、显示设置、原生异步和预设。
- **技能**：任一方关掉的来源或技能，子 Agent 里都关闭（`disabledSkills` 相加，来源两边都开才开）。冻结的技能设置同时决定 skills 工具描述里列出哪些技能和能加载哪些技能：被关闭的技能按名字加载也找不到，顶层对话同样适用。
- **工作环境**：新建子 Agent 时与父轮次取交集；之后每一轮（父或团队续派，以及用户在子 Agent 对话里开始的轮次）都与子 Agent 上一轮冻结的工作环境取交集，并沿用它的默认环境；该对话显式选了环境时用所选环境，所选环境不在允许范围内则报错。

后果：父对话没有的工具和技能，子 Agent 也用不了。想让只负责分派的 Agent 派出能执行命令的 worker，父 Agent 自己的工具设置里也要允许该工具。本规则之前建立的子 Agent，首轮没有边界记录，工具和技能按原规则运行。

## 工具与投递

- `run_agent` 继续管理创建、排队续聊、读取、等待和停止直接子树。
- `list_agents` 只返回同根团队成员。
- `send_agent_message` 保存同伴消息，普通空闲目标不启动新 Turn。
- `followup_agent_task` 提交明确任务；活动目标在安全边界接收，空闲目标通过原调度器继续执行。
- `read_agent_messages/wait_agent_messages` 有界读取和等待，不改变处理状态，不启动目标。`read_agent_messages` 用 M# `messageRef` 读取一条协作消息的全文时按页返回：每页至多 2400 个估算 token（`COLLABORATION_TEXT_PAGE_TOKENS`）和 12000 个字符，附 `offset`、`nextOffset` 与 `totalCharacters`，不拆开代理对；沿 `nextOffset` 读到 `null` 即得全文。`view=conversation` 时用 R# `messageRef` 以同样方式读取团队成员的一条对话消息。消息的发送方与接收方都能读，团队成员与跨对话的双方相同。
- 留言板代码保留，但第一期不向模型下发 `agent_board`。

发送可选择排队到目标本轮结束：目标正在运行时，消息锚定当前 Turn 且不注入该 Turn；该 Turn 结束后，followup 由持久唤醒开启恰好一轮新 Turn，message 随目标下一轮带入。跨对话 followup 还要求整轮独占，见下文「跨对话协作」。排队等待期间不做周期轮询，不拥有目标对话的宿主也一样：目标轮次结束的提交在本宿主直接触发扫描，其他宿主的提交或该轮的恢复通过外部数据版本变化触发扫描。完成后自动回送的结果不排队，仍在请求方运行中的 Turn 安全边界注入；请求方没有运行中的轮次时，团队回复随下一轮带入，跨对话任务的回复则开启请求方的一轮（见下文「跨对话协作」）。若用户在该轮吸收前停止它，这条结果与其他投向该轮但还没被吸收的 message 一样改回等待下一轮：该轮的结束提交在同一事务里完成这一步（读取之后才送达的，提交会失败并重新读取），所以紧接着开始的下一轮一定能读到，不会与唤醒扫描竞争而漏到再下一轮。之后 message 和团队回复的唤醒随即结清，不再为它重试或让对话一直显示忙碌；跨对话任务的回复则立即开启请求方的新一轮，不必等完它轮询已结束轮次时留下的退避。

手动压缩和从原始记录重建摘要的维护轮次不接收任何投递：开始时不带入等待下一轮的消息，运行期间到达的消息、回复和任务（包括重启后恢复扫描推进的投递）也不注入它，而是等它结束后由下一个真正的轮次带入或开启；团队的运行中成员通知把它视为空闲。

消息正文保存到 CAS；消息、来源、目标、回复关系、任务请求和请求对应 Turn 分别持久化。每条协作消息正文为 1 到 64000 个 UTF-8 字节（常量 `COLLABORATION_MESSAGE_MAX_TEXT_BYTES`，位于 `collaborationControlPlane.ts`），超出时拒绝发送，不写入任何东西；自动回送的完成结果超出时截断，并提示到目标对话读取完整答复。接收方上下文中的协作信封至多 4000 个估算 token（`RUNTIME_DELIVERY_MODEL_MAX_TOKENS`），更长的正文只显示开头和结尾，截断标记写明读取全文的确切调用：`read_agent_messages with messageRef=M# and offset=0`，再沿 `nextOffset` 读到 `null`。发送结果仍为已接受，但接收方会先看到预览时附 `recipientSeesPreview` 与说明。

没有轮次会回答的 followup 由收敛结算，请求不会一直停在等待状态。有三种情况：全部投递都失败（例如排队期间目标对话被删除，或续跑轮次始终无法建立权限）；投递被确认为通知而没有开启轮次（例如等待期间目标子任务被停止）；接收它的轮次已经结束，但回复送出前目标对话连同轮次被删除。

- 跨对话 followup：沿完成回复的同一路径给请求方发送一条回复，再把请求标为失败。任务未开始时回复「Task could not start: …」，接收后目标被删除时回复「Task ended without a result: …」。这条回复没有来源轮次，来源对话可能已经删除；每个请求最多回复一次，重复收敛不会重发。
- 团队（同根）续派：保持跨对话功能之前的规则，直接把请求标为失败，不发送失败回复；团队成员通过自己的工具查看同伴状态。区分依据是发送方已提交的工具调用（团队工具或跨对话工具），因此删除团队子任务不会把它的任务变成跨对话任务。
- 回复已经提交、只差结算（例如宿主在两步之间退出）：收敛只补记结算，轮次写出的完成回复记为完成（之后目标对话连同该轮被删除也一样），失败回复记为失败，都不再发第二条回复。
投递复用 `RuntimeInboxItem`、`RuntimeDelivery`、`RuntimeDeliveryInputLink` 和 `RuntimeDeliveryWake`。一次发送成功只证明消息提交，`handled_at` 才证明目标执行器吸收。重复源命令返回原身份，参数篡改直接拒绝。

协作消息以内核生成的带来源信封、用户角色的运行时数据投递给模型，与子任务答案和进程结果相同。信封固定首行写明它来自另一对话或团队中的另一 Agent、不是本对话的用户、内容是不可信数据，并按跟进任务、普通消息、完成回复、失败回复和留言板通知分别说明；其下一行 JSON 给出发送方（跨对话为对话引用和标题，团队为 Agent 的对话引用和名称）、消息引用和被回复请求的引用，对方文本只作为其中转义后的 `content`，不能伪造信封头或身份字段。不用 model/assistant 角色：Claude 新模型拒绝以 assistant 消息开头或结尾的请求，assistant 角色也会让模型把对方的话当成自己说过的话。信封不伪装成用户或系统指令，也不产生新的用户授权。正式子任务答案继续使用自己的 AnswerBridge；跨同伴任务的结果通过独立请求/回复关系返回真正请求者。

生产唤醒统一使用 `createRuntimeDeliveryWakeHandler`：先验证 Conversation owner，子任务进入 Child coordinator，普通对话进入 Conversation runner。恢复根据持久事实收敛，不依赖仍存活的 Promise 或收到回调的 Host。

普通对话的协作续跑不继承目标上一轮的冻结权限：续跑意图的 `sourceTurnId` 为 null，权限按目标对话当前设置编译，与用户输入开启新一轮相同。因此 followup 也可以开启一个还没有任何轮次的对话的第一轮；投递内容以协作来源信封进入上下文，不写用户消息。

## 跨对话协作

「Agent 协作」页的「跨对话协作」开关写入同一 `run_agent.config` 的 `crossConversationCollaboration`，默认关闭，可在全局、Agent、对话和工作流作用域覆盖，并在 Turn authority 中冻结。只有布尔值 `true` 表示开启；手工写入的非布尔值（例如字符串 `"true"`）按关闭处理，不会让整轮失败。

开关就是授权（决定 §7.18）：后端按轮次冻结的开关直接向顶层对话提供并放行下列五个工具，不看工具列表；设置界面开关只写开关值本身，不写入任何作用域的 `allowedTools`。因此上层保存了不含这些工具的列表、下层各自保存了列表，或全局关闭而某个 Agent 自己开启，结果都只由该轮生效的开关决定。唯一与列表有关的规则是 `run_agent`：Turn 的有效工具列表不含 `run_agent` 时，只提供并放行列出和读取两个工具，发送、新建和分支都不提供；之后给列表加回 `run_agent`，发送类工具随下一轮出现，不需要其他改动。这五个工具的名字在任何工具列表里都被忽略：解析时从列表和默认工具集中去掉，设置页下一次保存列表时也会去掉；以前保存的 `crossConversationGrantedTools` 字段不再有意义，读取时忽略，不做迁移。开关是唯一的开关控制，工具设置里不能单独停用其中某一个工具，只能逐个把执行确认改为每次确认（`toolConfigs[工具名].autoApproveExecution: false`）。工具设置页把这五个工具显示为由开关控制（勾选框不可用），「Agent 协作」里的说明显示当前实际生效的状态：关闭、只提供列出和读取，或全部五个。工具设置的「恢复继承」只重置工具设置，保留「Agent 协作」里保存的开关和协作上限。

- `list_conversations`、`read_conversation`（只读）：列出发起对话所在项目的其他活动顶层对话（见下文「项目范围」），读取其用户与模型消息，不启动、不改变、也不确认目标。结果附不可信数据提示。
  - 每页从最新消息开始花预算：条目合计至多 3000 个估算 token（`TRANSCRIPT_PAGE_TOKENS`），单条至多 2000（`TRANSCRIPT_MESSAGE_PREVIEW_TOKENS`），整个结果低于 4000 token 的工具结果上限，最后的答复总会显示。
  - 放不下的更早消息不列出，也不冒充超长消息：结果给出 `olderMessageRef`，以 `beforeMessageRef` 接着读，并附说明。
  - 超长消息只显示开头，标 `truncated` 并给出 `nextOffset`；用 `read_conversation` 的 R# `messageRef` 加 `offset` 按页读取全文。列举时不读取超过 256000 字节的消息正文，只给大小，全文同样按页读取。
  - 轮次收到的协作任务、消息和回复以 `role: collaboration` 条目排在该轮消息之前，附来源对话和模式，正文至多 400 个估算 token。分支不复制这些投递，所以分支的记录里没有它们。
- `send_conversation_message`：`followup` 或 `message`，固定排队到目标本轮结束；followup 完成后的回复自动回到发送方。
  - 跨对话 followup 只由它自己开启的那一轮消费，这一轮也只使用这条请求的预算。用户新开的轮次、其他对话的续派轮次、进程或子任务结果触发的续跑都不会吸收它。
  - 派发时目标只要有轮次在运行（包括锚定轮结束后才开始的用户轮次），followup 就继续等待，不注入该轮；该轮结束后再开启自己的一轮。
  - 多个对话排在同一轮之后的 followup 按发送先后（发送事务分配的消息序号 `message_seq`，不看时间戳，同一毫秒或时钟回拨都不会打乱）依次各开一轮，从不合并；较新的任务不会一再抢在较早的任务前面。用户停止目标的运行轮次时，排队的 followup 仍会立即开启新一轮。
  - `message` 仍随目标下一轮带入，不论这一轮由谁开启。
  - followup 的完成回复和失败回复（「Task could not start: …」「Task ended without a result: …」）送达时，发送方有轮次在运行就在该轮安全边界注入，不另开一轮；该轮已产生最终输出或是压缩等维护轮次时，等它结束。发送方没有运行中的轮次（包括用户刚停止它）时，回复开启发送方的一轮来处理它。这一轮花费这条任务所在任务链的自动续派预算，由开启它的事务检查并计数；它再派出的 followup 也花同一预算，所以两个对话来回续派和回复的往返同样以预算为界。预算用完时不开启轮次也不报错，回复随发送方下一轮带入。发送方对话已删除时跳过。每条回复最多开启一轮：唤醒重放或另一个宿主再次派发都只会找到已提交的那一轮。团队回复和普通 `message` 不自动开启轮次。
  - 团队内（同根）的续派语义不变。
  - 工具说明告诉模型答复怎样回来：发送方本轮仍在运行时加入本轮；本轮已结束时，在自动续派预算允许的范围内自动开启一轮处理，否则随下一轮带入。要在本轮内拿到答复，用 `wait_agent_messages`，把 `afterMessageRef` 设为本次调用返回的 `messageRef`；`create_conversation` 相同。
- `create_conversation`：以工具调用派生稳定对话身份并领取运行归属。写入任何东西之前，先检查开关、发送方仍是活动轮次中未结束的工具调用、每轮新建与分支上限和自动续派预算；然后只在空位中写入发送方冻结的工作环境和模型配置，最后在同一个事务里建立对话、主 Agent 关联、项目关联并提交 followup 任务。被拒绝或中途中断时不会留下空对话；准入之后才被拒绝（预算被同一链上的其他轮次用完、发送方轮次已停止、设置写到一半失败）时，在同一运行归属下清除已写入的工作环境和模型配置，清除失败只记日志，不掩盖原来的错误。只有宿主在提交前退出才会留下没有对话引用的配置，重放同一调用时复用它们，只补齐缺少的步骤；重放在准入时被拒（例如同一轮已达上限或预算已用完）则清除它们，但只在读到该确定 id 下确有遗留的模型配置或工作环境链接时才取设置锁清除，普通拒绝不清除任何东西。首个任务就是持久的创建标记：对话被用户删除后，重放同一调用会被拒绝，不会重新建出空对话。不写 `ConversationOriginLink`。
- `fork_conversation`：以工具调用作为分支命令身份，复制到最后一个已结束轮次的最后可见消息为止的历史，包括正在运行的调用方自身（native 与非 native 均适用）。与用户分支一样，在分支提交前复制源对话的对话层设置。分支不启动轮次，不切换用户视图；重放沿用已提交的分支边界。
  - 分支要在源对话的运行归属下读取并收口源历史：源对话由另一个 VS Code 窗口打开时拒绝，错误说明只能在那个窗口分支。列出、读取和发送不需要归属。
  - 工具调用只尝试一次：任何失败（永久拒绝、源对话被并发改动导致提交断言失败或其他错误）都在目标对话没有建立时清除已复制的对话层设置，并把错误改写为说明原因且写明「Nothing was created」的文字，不把内部断言原样交给模型。
  - 分支（以及带上下文分叉的子 Agent）保留源历史里的对话与协作消息引用。模型侧运行时卡片给出 `selfConversationRef`、`forkedFromConversationRefs`（复制历史里说的「本对话」指它们，由近及远）和 `inheritedMessageRefs`（在此不能读取或回复）。误用继承的消息引用时，错误说明它来自分支时复制的历史；回复时改为不带 `replyToMessageRef` 发送。

跨对话协作不新增设置，只复用已有预算并加几条固定上限（常量 `CROSS_CONVERSATION_LIMITS`，位于 `collaborationPolicy.ts`）：

- 跨对话 followup 和 `create_conversation`（首个任务就是 followup）都计入同一个 `maxAutomaticFollowups` 自动续派预算，写入任何事实之前先检查。跨对话回复开启的请求方轮次也计入，在开启该轮的事务里检查。
- 预算上限冻结在开启这条任务链的轮次里。该对话被删除后，它派出的任务仍能完成本轮工作、发送普通消息和读取对话，但不能再续派或新建对话：工具返回明确错误「The conversation that started this task was deleted…」，不写入任何东西。预算记录没有单独保存上限，这样不需要改动 schema；删除发起方也就结束了它资助的自动续派。
- 每个目标对话最多积压 16 条尚未投递或消费的入站协作消息（`message` 与 `followup` 都计入，来自任何发送方）；超过时拒绝跨对话发送，错误写明目标已有多少条未读协作消息，并说明在目标下一轮开始吸收它们之前，任何消息或续派都无法排队，不提示模型做不到的补救。回送给目标自身请求的完成回复不受限制，也不占积压名额。提交时只断言计入积压的这组投递，目标上无关的进程或子任务结果投递不会让发送失败；并发发送连续四次改变积压时，返回可重试的明确错误，不写入任何东西。
- 同一个发送轮次的 `create_conversation` 与 `fork_conversation` 调用合计最多 8 次，按已提交的调用顺序计数，重放结果不变。
- 超过上限时工具返回明确错误，不写入任何东西。

这些工具只下发给顶层对话；开关关闭或当前对话是子 Agent 对话时不下发，伪造调用也被执行器和协作控制面按冻结 authority 拒绝。发送类工具默认自动批准，用户可以在工具设置中逐个要求确认。对方文本始终以带来源的协作信封进入上下文，不成为用户消息，也不授予任何用户授权。

### 其他已定事项

- 关闭发送方的开关不撤回已经排队的 followup。开关在发送时按发送方轮次冻结的 authority 检查；已提交的任务照常在目标开启自己的一轮，完成后回复发送方。
- 顶层对话之间的扇出没有额外上限。只受自动续派预算、每个目标 16 条积压和每轮 8 次新建或分支这三条约束。
- 团队内父子之间的协作消息仍以协作卡片显示，与跨对话消息相同。
- 没有轮次会回答的任务：跨对话 followup 给请求方回一次失败回复；团队续派只把请求标为失败，不回复，保持跨对话功能之前的规则（见上文「工具与投递」）。开启轮次的预算也按同样的划分：只有跨对话 followup 开启的轮次独用这条请求的预算；团队和子任务的续跑仍汇总它吸收的请求，多个独立根预算不能合并。
- 跨对话任务的回复（完成或失败）送达空闲的请求方时开启一轮（用户停止之后也一样），花费并沿用它所回复请求的预算；预算用完时回复等待下一轮，不报错。团队回复和普通消息不自动开启轮次。

### 项目范围（已定）

跨对话工具只作用于与发起对话同一项目（`ConversationProjectLink`）的对话：列出、读取、发送和分支都限于当前项目，新建的对话建在当前项目。Runtime 由所有 VS Code 窗口共用，边界是项目而不是 Runtime。项目关联只在对话创建时写入、随对话删除，存续期间不会改变，因此检查不需要事务断言。

每次读取、发送和分支都由协作控制面按目标对话的项目检查，不论引用从哪里得到（列表、同伴消息或分支复制的历史）：其他项目的对话一律拒绝，错误说明它属于另一个项目，不读取、不发送、不创建任何东西。

未绑定项目的对话（空窗口或多根工作区里默认新建的对话）只与其他未绑定的对话互通，与侧栏的「未绑定」分组一致。一律拒绝会让这些窗口里的对话连自己新建的对话也无法续派或读取；而已绑定项目的对话无论哪个方向都与未绑定的对话隔离。

### 只由发送方授权（已定）

跨对话协作只检查发送方：发送方轮次冻结的开关决定能否列出、读取、发送、新建和分支，范围限于发起对话所在的项目。目标对话自己的开关不参与判断，也没有目标方确认，与 Codex 的 `codex_tui` 跨任务工具一致。这是有意的决定，不是遗漏。

目标收到 followup 后按自己当前的设置运行。防线有两条：对方文本始终放在带来源和不可信数据提示的协作信封里；信封虽以用户角色的运行时数据进入上下文，固定首行声明它不是本对话的用户，永远不获得用户文本的授权级别。需要更严格控制时，用户可以在工具设置里要求发送类工具每次确认。

## 上下文继承

`run_agent.spawn.forkTurns` 接受 `none`、`all` 或正整数文字，默认 `none`。只复制当前上下文可达的已完成轮，压缩后按来源恢复；排除当前未完成轮及旧 system/runtime_context，不继承原 lease 或 ChildExecution 控制关系。复制的轮次各自持有其历史 AuthoritySnapshot 的副本，只作为历史记录；子 Agent 自己的轮次仍按其任务编译权限，不沿用父对话轮次的冻结 authority，工具、技能与工作环境受上文「子 Agent 的工具、技能与工作环境边界」约束。继承历史、新任务正文、新子会话和父子关系在同一事务建立。

## 留言板与边界

频道、帖子、作者、回复和订阅各有独立领域表/Link。帖子完整正文保存在 CAS，读取按字符范围分页。通知只包含引用和有界摘要，完整正文通过读取帖子取得。

留言板通知只服务当时正在执行的目标 Turn；空闲目标不启动，也不保留下一轮才出现的通知。帖子本身持续可读，通知失败不能删除帖子或宣称通知成功。

## 存储与验证

新增协作领域使用当前 Runtime epoch 5。旧 epoch 通过已有 archive/reset 流程归档运行数据并建立当前 Runtime，保留配置和 Workspace；不增加任意旧格式的迁移或 fallback。当前 epoch 的缺表、索引、manifest 或 RootBinding 漂移继续 fail closed。

回归覆盖真实 SQLite/CAS、团队作用域与跨团队拒绝、跨对话开关与子 Agent 拒绝、跨项目拒绝、跨对话新建与分支、长消息与对话记录的分页读取、分支继承引用、静默消息、唤醒与处理 ACK、重复提交、并发预算、结果回信、分页、压缩/native 短引用、fork 和生产调度链路。界面检查包括继承/恢复设置及窄屏布局。统一入口为 `npm run check:local`。
