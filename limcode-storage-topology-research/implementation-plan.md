# LimCode 存储拓扑实施计划

制定及优先级更新日期：2026-09-26。依据：[研究报告](report.md)、归档实验结果、[业界架构补充](industry-comparison.md)及本轮维护者决定。源码核对基线为 `11ce63e195c667c78154e8560e598a1024f69b01`，package 0.0.28、Runtime epoch 5，与研究基线一致；后续开工须核对实际 HEAD。

本文是新增的决策与实施计划，不属于原研究的摘要校验集合。截至 2026-09-26 本地验收，epoch 3/4 历史恢复入口的本地实现、编译和定向回归已完成，当时尚未发布；该验收未验证客户实际数据。文中进度记录这一验收时点，后续发布状态以 [GitHub Release](https://github.com/lurenxing628/limcode-test/releases) 为准。其余工作仍按下列计划推进。历史源码与修复前证据见 [epoch 3/4 恢复审计](epoch3-4-recovery-audit.md)。

## 1. 当前决策：优先交付 A 中解决客户问题的工作

**采用 A，最高优先解决已发布 epoch 3/4 旧数据无法使用：发现可认证旧库后自动备份并原位升级，再通过历史入口读取。随后推进查询、跨项目刷新、执行归属与内容增长治理。** 每个数据根继续保留一个选中的共享 Runtime SQLite；各旧库仍作为独立数据集存在，合并由后续受控导入处理。

维护者已明确先解决 epoch 3/4 旧数据无法使用，无法联系受影响用户时自行核对历史源码，并要求直接自动备份升级，不增加升级按钮或确认步骤。当前选中旧库沿用启动时自动升级；当前 Runtime 正常打开后，在后台串行升级发现的其它旧库；查看旧历史时自动补做尚未完成的升级。优先关闭这一问题，再发布性能与执行边界改进。

自动升级复用已有精确迁移器，会修改旧 SQLite 的格式并保留升级前 SQLite 备份和原有 CAS；不是“来源字节保持不变”的隔离转换。多个合法库之间的当前数据集选择仍沿用既有显式选择规则；无法认证或忙碌的库记录失败，不能自动改选空库。非当前库的升级不启动其历史任务。

适用前提：当前核心产品仍为 VS Code 扩展，多个 Host 使用同一机器上的本地数据根；项目独立升级/停机尚未成为硬要求。该方案允许保留多个历史数据集，并不要求把旧库先物理合并。

需要后台持续运行、Desktop 或多客户端统一调度时，可以增加 D（每数据根一个共享服务）。D 与存储拓扑独立，同样可以管理 B 的多个项目库。A 全部完成不是 B/D 的前置条件；当前先交付客户修复，后续在每个复审点按需求与实测决定是否独立启动 B/D。

| 方案 | 本计划的选择 | 进入条件 |
|---|---|---|
| A：共享库补强 | 当前主线 | 查询、跨 Host 刷新、执行归属和体积问题已有明确修复入口 |
| B：按稳定项目 ID 分库 | 条件性替代 | 独立项目维护成为硬要求，或真实负载证明单库写锁是瓶颈且分片对照确有收益 |
| C：全局索引与项目分片 | 仅按需要引入可重建检索索引 | 不让派生索引承担执行授权、恢复或终态判定；跨库运行事实另立完整事务设计 |
| D：共享服务 | 条件满足时独立立项 | 后台运行、Desktop、多客户端能力路由进入明确交付范围；可与 A/B 组合 |
| E：追加日志作为运行权威 | 不进入本计划 | 需要重建现有多领域原子提交与恢复机制，目前缺少对应收益证据 |
| F：按窗口/工作区拓扑分库 | 不作为长期边界 | 窗口变化不能稳定表达项目身份 |

这是一项有条件的架构选择，不是共享库容量已经得到证明。SQLite WAL 仍然只能同时有一个 writer，共享服务也不改变这个约束。[SQLite WAL 官方说明](https://sqlite.org/wal.html)

P2 不依赖 P0 压测、COUNT 优化、精细刷新、GC 或导入；先按历史可用性验收并发布。后续 COUNT 修复也不要求先完成完整四 Host/全平台容量研究，P0 的最小复现和度量随改动建立。P3 的技术依赖是自身范围识别、可靠提交与升级合同，不要求 BUSY 重试、GC、导入全部完成。B/D、项目身份重构、pack 和在线 GC 不列入当前历史恢复批次。

## 3. 技术工作包与交付边界

以下 P0–P5 是沿用的技术工作包编号，**P2 当前优先级最高**，实际发布批次以 §1.2 为准。量级参考原报告，为单维护者估计，不是日历承诺；本轮 P2 已缩小到复用现有迁移器的自动恢复入口，其进度按实际验收记录。

| 阶段 | 交付结果 | 关键验收 | 粗量级 |
|---|---|---|---|
| **P2：自动恢复旧历史，最高优先** | 认证旧库→自动一致性备份→原位精确升级→历史读取；启动后串行处理其它旧库 | 无升级确认；保留原事实、SQLite 备份和 CAS；非当前旧任务不启动；单库错误隔离 | 本地验收时完成，当时待发布验证 |
| P0：真实基线 | 可重复的多 Host Runtime 负载与诊断 | 统计所有请求的排队、锁等待、重试、失败和刷新 bytes，识别实际瓶颈 | 2–4 个工作日 |
| P1：查询与执行边界 | 项目 COUNT 优化、合并轮询、恢复与审批资格、有限事务重试 | 计数语义一致；无资格 Host 不自动接管；取消/超时有界；外部 effect 不重放 | 1–2 周 |
| P3：跨 Host 精细失效 | 持久 scope revision、范围化正文/导航/工作扫描、项目分页游标 | 无关项目 100 次提交不产生正文快照或重置本项目分页；删除/重连/崩溃后仍收敛 | 2–4 周，含精确 epoch 升级 |
| P4a：内容写入减量 | native 累计展示由规范 item 内容重建；减少冗余长期内容 | 最终输出、Context、fork 和恢复语义等价；增长曲线改善 | 2–4 周 |
| P4b：保守空间回收 | 离线 GC、预览、隔离区、恢复 journal | 所有有效引用与备份均可读；中断和磁盘满不误删 | 2–4 周 |
| P5：受控导入 | 已终结闭合子图导入、严格冲突处理、幂等恢复 | 不意外继续旧任务；同 ID 异内容拒绝；崩溃后可验证恢复 | 3–6 周或更长 |

依赖关系：P2 复用已有精确迁移器、admission/maintenance 和备份恢复协议，独立于性能工程，先完成。随后 P0 最小诊断与 P1 查询改动并行；P3 使用可复现 Feed 基线，并与统一检测/消费者确认接口衔接，不依赖 P1 的重试与执行资格全部结束。P4a 与 P3 可并行审计；P4b 在 retention roots 完整后交付。P5 自行建立来源快照和导入 staging，不把 P2 原位升级误当作隔离导入工具。

### P2：最高优先，自动备份升级 epoch 3/4 旧历史

关键入口：新增 `runtimeDataSetUpgrade.ts`，以及 `runtimeDataSetHistory.ts`、`runtimeEpochMigration.ts`、`vscodeRootAuthority.ts`、`runtimeHostControl.ts`、`vscode/commands/runtimeDataSetManagement.ts` 和扩展启动接入，以及 `vscode/runtimeDataSetUpgradeLifetime.ts`。本地实现、编译与定向回归已完成，具体结果和边界见恢复审计 §8。

流程：发现旧数据集 → 精确认证 epoch 3/4 与身份 → 在 admission/离线维护边界内自动建立 SQLite 备份 → 调用现有精确迁移器原位升级 → 校验 → 按需只读查看。备份使用 [SQLite Backup API](https://sqlite.org/backup.html)，包含已提交 WAL 事实；不能复制活动 DB/WAL 冒充一致性快照。

- `upgradeRuntimeDataSet` 严格复用已有精确迁移器，不另建宽松迁移链；保留备份、原有 Conversation/Message/附件与 CAS。旧 SQLite、manifest 与绑定 generation 会按既有合同升级；必要的历史 continuation 转换可以新增 CAS 内容。
- 当前选中 epoch 3/4 沿用既有 startup 自动升级。当前 Runtime 正常打开后，后台调用 `upgradeDiscoveredRuntimeDataSets` 串行处理发现的其它旧库；单库失败收集为诊断并继续处理其它候选。
- 用户查看旧历史时自动补做尚未完成的升级，再打开只读句柄。没有升级按钮或升级确认；这是用户已授权的默认行为。目标正被其它 Host 使用、来源未知或校验失败时保留原数据与已有备份，报告原因，不能自动重置。
- 候选枚举区分合法旧库、空残留、只有备份的 scope 和真正异常的根；一个异常 scope 不再阻断其它合法旧库的管理与后台升级。当前数据集选择存在歧义时仍沿用既有显式选择，不自动改选或新建空库。
- 其它旧库的升级不切换当前数据集，不合并多个旧库，不注册其执行 Host，不启动其 startup recovery。只读句柄仍以来源身份定位，防止同 ID 跨库混淆。
- 验收自动入口、备份先于变更、原有事实与 CAS 保留、当前选择稳定、非当前旧任务不启动，以及 WAL-only 提交、未知指纹、pending、磁盘满、并发维护和重复执行。关闭或更换配置根后，旧后台扫描不得继续调度新来源。

未来另行设计“来源业务字节不变的隔离副本转换”和移动/归档备份的重新绑定恢复；它们不属于本轮原位自动升级，也不阻塞当前历史可用性修复。已经移位或只剩归档的来源不能通过忽略 RootBinding 路径来强行打开。

### P0：历史恢复后补充真实负载基线

- 在隔离数据根运行真实 Runtime：四个 Host，分别覆盖四个活跃项目及同项目多 Host；加入流式输出、工具结果、子任务、审批、历史翻页、删除和重连。使用可控 provider/capability 夹具驱动实际内核，不发送真实外部操作。
- 建立可重复的到达率与突发负载；除闭环吞吐外记录排队积压，避免等待使请求减少而掩盖饱和。按场景报告成功、失败、超时、取消，不能只计算成功请求分位数。
- 记录 worker 排队、事务持锁、原生 busy 等待、重试总时长、正文快照数量/bytes、最老读事务、WAL 未完成 checkpoint 页及 CAS 发布耗时。诊断不含正文。
- 单列常规交互和维护负载。第一轮使用现有 Linux 环境，各发布批次补齐改动涉及的目标平台验证；完整 Windows/macOS 容量基线和 WAL/NORMAL 与 FULL 的持久性评估分别推进，不作为开始 COUNT 修复的前置工程。
- 首轮及 P3/P4a 后各设置一次架构复审点。若一开始就确认独立项目维护是硬要求，立即走第 6 节的 B 路线，不必等完整治理结束。

### P1：历史恢复后可独立发布的查询与执行修复

关键入口：`backend/reliableKernel/clientProjection.ts`、`databaseSchema.ts`、`databaseWorker.ts`、`runtimeDatabase.ts`，以及 `backend/application/reliableKernel/ExternalDataVersionWatcher.ts`、`VscodeReliableKernelApplicationFacade.ts`、`VscodeReliableKernelProductRuntime.ts`、`ReliableConversationRunner.ts`、`interactionAttention.ts`、`VscodeReliableToolHost.ts`。

1. COUNT 使用现有 ProjectContext/ConversationProjectLink 索引，保持 all/project/unbound、删除和权限语义。该查询改动保留现有 total 协议；是否改为懒计数由 UI/协议一起设计，不隐式改变返回含义。
2. 每个 Runtime/Host 合并外部变化检测，共用同一连接的观察基线；各消费者刷新成功后分别确认进度。任何消费者失败仍须重试。此阶段仍可保守刷新，精细范围由 P3 提供。
3. 恢复前校验项目、冻结工作环境、可用能力和交互归属；默认本项目合格 Host 才自动认领。多根窗口按其明确提供的项目能力匹配；无人合格则保留等待并说明原因。审批和 diff 路由使用同一资格依据，同项目多 Host 仍由 owner/fence 决定承接者。
4. 明确取消和请求 deadline，再实现 BUSY 重试。同步 better-sqlite3 的一次 `busy_timeout=5000` 会阻塞 worker；必须限制单次原生等待并按剩余预算安排重试，让队列能处理取消。外层增加短退避本身不解决五秒阻塞。
5. 仅在确定事务未提交、回滚完成后重放可重算的数据库 steps；每次重验绑定 generation、owner/fence 和事务断言。未知提交结果先对账，不自动重放；网络、工具和 CAS 外部操作不进入重试事务。

验收覆盖查询等价与 EXPLAIN、多 Host 竞争、退避中取消、过期 fence、同项目接管、无 Host 可接管、重复审批响应及两窗口 UI。若 UI 归属需要新增持久关系，先完成合同并纳入明确 epoch，不用未受保护的内存映射冒充可靠归属。

### P3：补齐跨 Host 精细失效

关键入口：`databaseWorker.ts`、`clientFeed.ts`、`clientProjection.ts`、`schema/domainManifest.ts`、各独立 Repository，以及 `docs/architecture/reliable-kernel/contracts/`。

建议采用最小的持久 scope revision，分别表达对话视图、历史列表、运行工作范围需要重查。每个事实变更与相关 revision 在同一事务提交；revision 不承载正文、ClientState patch 或第二套运行队列。

- 先完成逐领域及派生依赖覆盖表，包含旧/新归属、独立 Link、父子关系、删除。删除后仍能发现失效，不能依赖被 cascade 删除的标记。
- 视图数据与其 revision 必须来自一致快照；启动订阅、读快照、确认进度之间不能漏掉并发提交。
- 正文仅关注当前对话及其真实依赖；导航按 project/all/unbound 范围失效。全历史列表在其他项目改变时更新是正常行为，不能为减少更新而漏数据。
- 项目分页游标绑定该 scope 的 revision 和 root generation，无关项目提交不 reset；all 范围仍响应所有相关列表变化。
- `PRAGMA data_version` 仅作为外部变化提示，同一连接前后比较；worker 内存 commitSeq 不升级为跨 Host durable cursor。[SQLite data_version 说明](https://sqlite.org/pragma.html#pragma_data_version)
- 通知丢失、重连、根切换时从当前事实进行有界重查。保留现有本地提交筛选、队列合并及 ACK 机制。

这些持久结构需要明确的新 epoch，建议下一次为 6。实施时先更新机器合同、指纹、AGENTS 当前定义和发布来源清单，再提供认证 epoch 5→6 的离线转换与中断恢复。既有 epoch 3/4 来源继续由精确离线工具覆盖，生产 Runtime 只打开当前格式；不引入任意版本协商或通用迁移链。

首批 epoch 只包含完成本阶段所需结构。ProjectLocationLink、导入账本、删除 job 等按各自成熟设计安排，不预先塞空表。`client_change_log` 禁令继续成立。

### P4：先减少新内容，再回收可删除内容

关键入口：`turnOutput.ts`、`nativeRequestSession.ts`、`modelProviderControlPlane.ts`、Context/Message projection、`contentAddressedStore.ts`、`runtimeStorageInspection.ts`、RootAuthority。

- 审计 native `cumulativeContent` 的读者，把只用于展示的累计前缀改为由 canonical item 内容生成。被 Context、fork、恢复和历史引用的 revision 必须保留有效语义。
- 用递增长度的 item 链测量每请求写入 bytes/对象数，另测读取与恢复耗时。压缩率样本不作为生产收益承诺。
- recipe 的冻结语义保持稳定；checkpoint 按恢复边界保留。已经存在的普通 delta 合并与终态裁剪不重复开发。
- GC 首版在维护边界内离线执行：枚举完整 retention roots，包括 SQL、typed CAS 引用、备份、历史快照和 pending publications；预览 → 持久化计划/意图 journal → 可重入 quarantine 并逐项记录进度 → 核验 → 删除并持久化完成状态。恢复须能识别意图已记录但移动结果尚未记账的中断，按源/隔离区身份核验后收敛。
- 验收正常退出、进程中断、磁盘满、取消和恢复；保留对象逐一可验证读取。不能把 19.27MiB 候选清单直接当删除清单。
- 用户内容默认保留。压缩、pack、在线 GC 在有收益证据和完整新合同后另做。

### P5：有界导入

先为全部 Runtime 领域建立 ownership/reference policy、命令事务写集合和 typed CAS 引用清单；空表也必须定义语义。将无显式归属回执追溯到精确来源；无法解释则拒绝对应完整导入，保留来源只读可见。

第一版只接受已经终结且引用闭合的集合；active/unknown effect、未决审批或投递留在来源。保留 ID；同 ID 同规范内容经核验后复用，不同内容拒绝整个闭合批次。暂不做全局字符串替换或自动重编号。

首版导入在目标 RootAuthority admission/maintenance 下冻结所有 writer 和相关配置变更，固定目标 generation，从一致性目标快照建立 staging。完整保留并核验目标原有事实、CAS 和配置，再加入来源事实；直到发布完成才解除维护。若要求导入期间继续写入目标库，必须另行设计增量追赶和切换协议，不在首版范围内。

通过隔离 staging、同事务批次 receipt、配置变更 journal 和原子 pointer 发布完成导入；CAS 先核验并持久发布再提交引用。验收包含维护期间拒绝新写入、目标既有事实完整保留、重复导入、来源变更、同 ID 冲突、配置引用、fork/子任务、共享 hash 多类型、每个 journal 边界中断与最终对账。

## 4. 建议采用的产品边界

- 任务自动恢复默认限于具备相应项目与冻结环境能力的 Host；跨项目后台接管由后续明确功能提供。
- 当前 project ID 先作为不透明稳定引用保留。项目移动通过未来独立位置关系表达；clone 默认分开，worktree 保留独立执行位置，不因 URI 相似自动合并。
- 当前阶段不开放活跃对话改挂项目。该变化涉及协作授权与完整子树，需独立事务设计。
- 用户会话/附件默认长期保留；诊断可以有界轮转，归档和删除由用户明确选择。
- 支持同一 OS 实例本地文件系统上的多 Host，包括 Remote Host 自己的本地磁盘；多机器共用 NFS Runtime 根不纳入本阶段。
- 持久性仍按现有 NORMAL 合同理解。在 P0 测量 FULL 和 CAS fsync 链后，单独定是否提升断电承诺，不把进程崩溃恢复等同于断电不丢确认事务。

## 5. 验收目标与发布门槛

以下是建议目标，不是现有实测结果。压测必须记录硬件、数据量、到达率、事务混合和观测时长。

| 范围 | 目标 |
|---|---|
| 常规四 Host 混合负载 | 数据库交互从入队到结果 p95 < 100ms、p99 < 300ms；失败/超时单列，不从指标隐藏 |
| 跨项目正文隔离 | 无真实依赖的项目连续 100 次提交，当前对话额外正文 snapshot 为 0 |
| 项目历史分页 | 同一场景下当前项目游标不因无关项目提交 reset；all/unbound 按各自真实范围响应变化 |
| 有关变更可见性 | 在正常负载和轮询预算内，候选端到端目标 ≤2.5s |
| 取消与长锁 | 请求在声明的总预算内结束；同步原生等待有上限；外部 effect 不重复 |
| epoch 3/4 自动升级与历史读取 | 无升级确认；先备份后原位升级并保留 CAS；单库失败不挡其它库；当前选择稳定，非当前旧任务不启动；未知结构明确拒绝 |
| 导入与 schema 升级 | 在各自明确的维护边界内执行；升级前备份保留，导入来源保留；目标既有事实无遗漏，中断可恢复，无静默重置 |
| 内容与 GC | 输出、上下文与恢复语义等价；有效引用、备份和历史读取无损 |

按改动完成编译、项目合同检查及相关可靠内核回归；涉及 UI 时补 Webview 类型检查和相应交互验证。首次 schema 变更、迁移、GC 发布须跑完对应故障注入夹具和适用平台检查。完整发布门槛以项目现有 `check:plan`、本地/CI 测试和 stage gate 合同为准，不能用研究期间中断的全量结果替代。

## 6. 改选方案的明确条件

本节与 A 客户问题交付并行维护。首批修复后、P3/P4a 实测后均复审；B/D 的条件一旦满足即可独立评估，无需等 A 所有工作包完成。[业界架构补充](industry-comparison.md)记录了两者的收益、代价及证据边界。

**转 B：** 出现以下任一业务/性能条件时启动专项设计：项目必须可独立升级/停机/恢复；或真实常规负载在收窄刷新、短事务和写入减量后仍无法达到约定目标，诊断证明主要受单库写锁限制，并且项目分片对照能改善。磁盘总吞吐耗尽时，分文件不构成充分理由。

采用 B 的发布前提：逐领域及逐命令闭合证明、稳定 projectId、独立 unbound 数据集、多个 Runtime 的有界 registry、活跃任务/审批 pin、跨库 keyset 历史聚合、独立配置作用域对账，以及可恢复的分片发布 journal。还须证明共享配置操作不会迫使所有项目停机。

**加 D：** 后台持续运行、Desktop、多客户端调度成为排期内功能。设计每数据根服务、认证 IPC、能力注册、审批路由、断连/升级和 unknown outcome 恢复；SQLite 提交事实继续作为唯一运行权威。

**引入 C 的派生索引：** 历史/检索实测需要时再建，可删除并从运行事实重建；其滞后不影响执行正确性。
